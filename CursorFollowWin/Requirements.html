Feature Requirements

CursorFollowWin

Build a Windows 11 equivalent of CursorFollow using C# and .NET, preserving feature parity and visual identity with the macOS app while using native Windows conventions for the system tray, capture APIs, settings, permissions, packaging, and virtual camera integration.

Target Platform Windows 11
Language C# / .NET
App Folder CursorFollowWin
Status Draft for dev review

Objective

CursorFollowWin must let Windows 11 users choose or automatically follow a target window, capture that window with low latency, preview the captured output, and expose it as a selectable virtual camera named CursorFollow Camera in apps such as Teams, Zoom, Slack, Google Meet, OBS, and browser-based conferencing tools.

Mac Parity Baseline

The Windows app should feel like the same product moved to Windows, not a separate utility with different behavior. Terminology, control hierarchy, default settings, and camera naming should remain aligned with the macOS app unless Windows platform behavior requires a different implementation.

Scope

In Scope

  • Windows 11 desktop app in C# and .NET under CursorFollowWin.
  • System tray resident app with compact control panel and settings dialog.
  • Visible-window enumeration, manual target selection, and auto-follow behavior.
  • Window capture with cursor included by default.
  • Virtual camera output named CursorFollow Camera.
  • Live output preview window with optional overlays.
  • Persistent settings, app startup option, hotkeys, and troubleshooting logs.
  • Build, install, verify, and reset documentation for Windows developers.

Out of Scope

  • Windows 10 support unless required later by testing.
  • macOS implementation changes.
  • Linux support.
  • Cloud accounts, sync, licensing, or telemetry services.
  • Advanced visual effects, transitions, annotations, or compositing beyond parity.
  • Mobile, Xbox, HoloLens, or Store-only distribution requirements.

Technology Decisions to Validate

Area Preferred Direction Validation Gate

Frame transport Prefer GPU texture sharing between capture and camera output. Use CPU BGRA copy only if simpler and still meets latency/CPU targets. End-to-end median latency stays below target during a 30-minute capture session.
Installer Windows installer that registers the app, virtual camera components, startup option, and uninstall cleanup. Fresh install, upgrade, and uninstall leave camera registration and settings in expected states.

Functional Requirements

  1. The app installs into a CursorFollowWin product folder and launches as a Windows 11 desktop tray application.
  2. The tray icon opens a compact panel with the same primary workflow as macOS: Auto-follow cursor, filter mode, window list, Refresh, Show/Hide output, status, and Start/Stop.
  3. The app enumerates visible capturable windows, including Win32, Electron, browser, Office, and packaged app windows where Windows permits capture.
  4. The app filters out desktop shell surfaces, system UI, tiny utility windows, CursorFollowWin itself, and known non-capturable windows by default.
  5. The user can manually select a window when filter mode is All.
  6. Exclude mode lets the user mark apps/windows that auto-follow should skip.
  7. Include mode lets the user restrict auto-follow to an approved set of apps/windows.
  8. Auto-follow switches capture target when the foreground window changes and respects the active filter mode.
  9. Auto-follow debounces rapid target changes to avoid capture thrash.
  10. Capture starts and stops from the tray panel without closing the app or unregistering the camera.
  11. The output preview window renders the live captured frame, preserves aspect ratio, supports resizing, and can be pinned above other windows.
  12. The virtual camera publishes a stable video stream named CursorFollow Camera.
  13. The virtual camera remains selectable even when capture is idle, missing permission, or the target disappears, using a clear fallback frame state.
  14. The settings dialog includes startup, auto-share on launch, hide when not sharing, pin output on top, capture quality, overlay display, and hotkey settings.
  15. Global hotkeys support toggling auto-follow and toggling sharing, with visible conflict/error feedback.
  16. The app persists settings per Windows user.
  17. The app provides actionable error states for missing permissions, protected content, camera registration failure, capture failure, and hotkey conflicts.

UI Requirements

Tray Panel

  • Width and density should feel close to the macOS panel.
  • Header shows app name, camera icon, live badge when capturing, settings button, and quit/close affordance.
  • Window rows show title, owner app, resolution, selected state, and filter membership indicator.
  • Start and Stop use clear green/red treatment matching the macOS intent.

Windows Fit

  • Panel opens from the system tray/taskbar area, not the top of the screen.
  • Use Windows 11 typography, spacing, focus rings, shadows, and high-DPI behavior.
  • Respect light/dark mode if practical; dark mode can be the initial default for parity.
  • Keyboard navigation and screen reader labels must be present for controls.

Settings

  • Two-column layout on desktop-sized dialogs, collapsing cleanly if narrower.
  • General, Capture Quality, Hotkeys, Display, and About sections.
  • Save and Cancel behavior should allow discarded draft settings.
  • Mutually exclusive settings must explain disabled state, such as hide when not sharing vs pin on top.

Non-Functional Requirements

Category Requirement Target
Latency Median capture-to-camera-output latency for live window content. Less than 50 ms median on the development Windows 11 machine.
Switching Target switch interruption when auto-follow changes windows. Less than 300 ms visible interruption.
Frame rate Balanced mode should prioritize smooth capture. 60 fps when source and machine support it; 30 fps performant fallback.
Resolution Default virtual camera stream resolution. 1920x1080 BGRA or equivalent camera-client-compatible format.
Stability Long-running capture session. 30 minutes with no crash, unbounded memory growth, or sustained CPU/GPU spike.
Accessibility Controls are reachable and labeled. Keyboard and screen-reader accessible for primary workflows.
Diagnostics Logs identify capture, tracking, virtual camera, installer, and permission failures. Actionable logs with component names and user-visible remediation where appropriate.

Implementation Phases

Phase 0: Virtual Camera Feasibility

  • Create minimal Windows 11 camera device prototype named CursorFollow Camera.
  • Publish generated test frames at 1920x1080.
  • Verify camera selection in Teams, Zoom, Slack, Chrome/Edge, OBS, and Windows Camera where applicable.
  • Document chosen virtual camera API, registration model, installer implications, signing needs, and unsupported clients.

Phase 1: Project Skeleton and Tray UI

  • Create CursorFollowWin solution structure, build scripts, and baseline app.
  • Implement system tray icon, compact panel, settings dialog, persisted settings, and app startup registration.
  • Match macOS visual hierarchy and naming while using Windows 11 placement and interaction rules.

Phase 2: Window Tracking and Capture

  • Enumerate visible capturable windows with app identity and geometry.
  • Implement manual selection, filter modes, refresh, foreground-window auto-follow, cursor-under-window follow if viable, and debounce.
  • Capture selected window with Windows Graphics Capture and render the output preview.

Phase 3: Live Camera Pipeline

  • Bridge captured frames into the virtual camera output path.
  • Handle resize, aspect ratio, idle state, missing window, protected content, and camera-client open/close events.
  • Measure latency, CPU, GPU, dropped frames, and memory behavior.

Phase 4: Packaging and Hardening

  • Create installer, upgrade path, uninstall cleanup, code signing plan, and developer verification scripts.
  • Add reset/troubleshooting docs for camera registration, capture permission, hotkey conflicts, and stale devices.
  • Run 30-minute stability tests and camera-client compatibility matrix.

Risks and Open Questions

Risk Impact Mitigation
Virtual camera API/client compatibility differs across Teams, Zoom, browser apps, OBS, and Windows Camera. Camera may appear in some clients but not others. Run Phase 0 first and maintain a compatibility matrix before committing to full architecture.
Some windows cannot be captured because of DRM, elevation boundaries, protected content, or OS restrictions. User may see black output or missing windows. Detect and explain protected/unavailable targets; keep virtual camera stable with fallback output.
GPU texture sharing into the camera stack may be complex. CPU copy path could raise latency or CPU usage. Prototype both minimal GPU and CPU paths; choose the simplest path that meets performance targets.
Windows startup, installer, and camera registration may need admin rights or signing. Developer setup and user install flow could be brittle. Document privilege requirements early and keep install/uninstall/reset commands repeatable.
Visual parity may conflict with native Windows expectations. App may feel either non-native or unlike CursorFollowMac. Prioritize product hierarchy and control names from macOS, but use Windows placement, focus, notification, and accessibility behavior.

Verification Checklist

Developer Verification

  • Build CursorFollowWin from a clean checkout on Windows 11.
  • Install the app and confirm the tray icon appears after launch.
  • Confirm CursorFollow Camera appears in supported camera clients.
  • Capture a selected window and verify the same content appears in preview and camera clients.
  • Switch active windows with auto-follow enabled and confirm the camera follows within the interruption target.
  • Stop capture and confirm camera clients do not crash or lose the device.

Acceptance Criteria

  • Feature parity is documented and implemented for the primary macOS workflows.
  • Tray panel and settings dialog look recognizably like CursorFollow while feeling appropriate on Windows 11.
  • Camera clients can select CursorFollow Camera and display live window content.
  • Missing permissions, unsupported windows, and target disappearance degrade gracefully.
  • Build, install, verify, reset, and uninstall steps are documented and repeatable.
  • Thirty-minute capture stability test passes without crash, major leak, or sustained performance spike.

Review Prompts

Use these questions during development review to flush out hidden platform assumptions before implementation starts.

  1. Which Windows virtual camera path gives the best compatibility across the exact target apps?
  2. Should the first implementation optimize for fastest parity or lowest latency architecture?
  3. Which UI framework best supports the tray flyout, Windows 11 styling, high-DPI preview, and developer velocity?
  4. What install flow is acceptable during early development if camera registration needs admin approval?
  5. How should the app communicate protected-content and elevated-window capture limits without feeling broken?
