Feature Requirements

CursorFollowWin

Build a Windows 11 equivalent of CursorFollow using C# and .NET, preserving the target-window tracking workflow while using native Windows conventions for the system tray, capture APIs, output-window sharing, settings, permissions, and packaging.

Target Platform Windows 11
Language C# / .NET
App Folder CursorFollowWin
Status Phase 3.5 gap analysis

Objective

CursorFollowWin must let Windows 11 users choose or automatically follow a target window, capture that window with low latency, and render it into a normal shareable output window. The intended meeting workflow is that users keep their real webcam selected while sharing the CursorFollow output window in apps such as Teams, Zoom, Slack, Google Meet, OBS, and browser-based conferencing tools.

System tray app Shareable output window Window capture Auto-follow Windows 11 visual parity C# / .NET

Mac Parity Baseline

The Windows app should feel like the same product moved to Windows, not a separate utility with different behavior. Terminology, control hierarchy, default settings, and target-window tracking should remain aligned with the macOS app unless Windows platform behavior requires a different implementation. The delivery surface differs intentionally: Windows prioritizes a shareable output window so the user's real webcam can stay active during calls.

Scope

In Scope

  • Windows 11 desktop app in C# and .NET under CursorFollowWin.
  • System tray resident app with compact control panel and settings dialog.
  • Visible-window enumeration, manual target selection, and auto-follow behavior.
  • Window capture with cursor included by default.
  • Live shareable output window with optional overlays.
  • Meeting-app window sharing workflow while the user's real webcam remains selected.
  • Persistent settings, app startup option, hotkeys, and troubleshooting logs.
  • Build, install, verify, and reset documentation for Windows developers.

Out of Scope

  • Windows 10 support unless required later by testing.
  • macOS implementation changes.
  • Linux support.
  • Windows virtual camera / Media Foundation camera source (decided out of scope June 2026; the MF feasibility spike was archived and removed). The shareable output window is the delivery path.
  • Cloud accounts, sync, licensing, or telemetry services.
  • Advanced visual effects, transitions, annotations, or compositing beyond parity.
  • Mobile, Xbox, HoloLens, or Store-only distribution requirements.

Technology Decisions to Validate

Area Preferred Direction Validation Gate
UI framework C#/.NET desktop UI that can deliver a polished Windows 11 tray app. Candidate frameworks: WinUI 3, WPF with modern styling, or .NET MAUI only if tray/flyout behavior is proven. Compact tray panel, settings dialog, dark theme, high-DPI rendering, and native notification-area behavior are working.
Window capture Windows Graphics Capture with Direct3D 11 interop for low-latency window capture. Captures a selected window at target frame rate, includes cursor, handles window resize, and does not capture protected content.
Window discovery Win32 enumeration plus UI Automation where needed for names, app identity, and focus tracking. Correctly lists normal app windows and filters system/tool windows across classic Win32, Electron, browser, and packaged apps.
Output window WinUI/Win2D or Direct3D-backed output surface that renders the captured target as a normal shareable window. Teams, Zoom, Slack, Google Meet/Chrome, Edge, and OBS can share the CursorFollow output window while a real webcam remains selected.
Frame transport Prefer GPU texture sharing between capture and output-window rendering. Use CPU BGRA copy only if simpler and still meets latency/CPU targets. End-to-end median latency stays below target during a 30-minute capture session.
Installer Windows installer that registers the app, startup option, and uninstall cleanup. Fresh install, upgrade, and uninstall leave app files, startup registration, settings, and logs in expected states.

Functional Requirements

  1. The app installs into a CursorFollowWin product folder and launches as a Windows 11 desktop tray application.
  2. The tray icon opens a compact panel with the same primary workflow as macOS: Auto-follow cursor, filter mode, window list, Refresh, Show/Hide output, status, and Start/Stop.
  3. The app enumerates visible capturable windows, including Win32, Electron, browser, Office, and packaged app windows where Windows permits capture.
  4. The app filters out desktop shell surfaces, system UI, tiny utility windows, CursorFollowWin itself, and known non-capturable windows by default.
  5. The user can manually select a window when filter mode is All.
  6. Exclude mode lets the user mark apps/windows that auto-follow should skip.
  7. Include mode lets the user restrict auto-follow to an approved set of apps/windows.
  8. Auto-follow switches capture target when the foreground window changes and respects the active filter mode.
  9. Auto-follow debounces rapid target changes to avoid capture thrash.
  10. Capture starts and stops from the tray panel without closing the app or destroying the output window.
  11. The output window renders the live captured frame, preserves aspect ratio, supports resizing, and can be pinned above other windows.
  12. The output window is intentionally shareable through meeting-app window pickers while the user's real webcam remains active.
  13. The output window remains stable when capture is idle, missing permission, or the target disappears, using a clear fallback frame state.
  14. The settings dialog includes startup, auto-share on launch, hide when not sharing, pin output on top, capture quality, overlay display, and hotkey settings.
  15. Global hotkeys support toggling auto-follow and toggling sharing, with visible conflict/error feedback.
  16. The app persists settings per Windows user.
  17. The app provides actionable error states for missing permissions, protected content, output rendering failure, capture failure, and hotkey conflicts.

UI Requirements

Tray Panel

  • Width and density should feel close to the macOS panel.
  • Header shows app name, camera icon, live badge when capturing, settings button, and quit/close affordance.
  • Window rows show title, owner app, resolution, selected state, and filter membership indicator.
  • Start and Stop use clear green/red treatment matching the macOS intent.

Windows Fit

  • Panel opens from the system tray/taskbar area, not the top of the screen.
  • Use Windows 11 typography, spacing, focus rings, shadows, and high-DPI behavior.
  • Respect light/dark mode if practical; dark mode can be the initial default for parity.
  • Keyboard navigation and screen reader labels must be present for controls.

Settings

  • Two-column layout on desktop-sized dialogs, collapsing cleanly if narrower.
  • General, Capture Quality, Hotkeys, Display, and About sections.
  • Save and Cancel behavior should allow discarded draft settings.
  • Mutually exclusive settings must explain disabled state, such as hide when not sharing vs pin on top.

Non-Functional Requirements

Category Requirement Target
Latency Median capture-to-output-window latency for live window content. Less than 50 ms median on the development Windows 11 machine.
Switching Target switch interruption when auto-follow changes windows. Less than 300 ms visible interruption.
Frame rate Balanced mode should prioritize smooth capture. 60 fps when source and machine support it; 30 fps performant fallback.
Resolution Default output-window size and scaling behavior. Start near 960x540 for generated/test output, preserve captured aspect ratio, and support crisp resizing.
Stability Long-running capture session. 30 minutes with no crash, unbounded memory growth, or sustained CPU/GPU spike.

Diagnostics Logs identify capture, tracking, output rendering, installer, and permission failures. Actionable logs with component names and user-visible remediation where appropriate.

Implementation Phases

Phase 0: Shareable Output Window Feasibility

  • Create a minimal Windows 11 app that renders generated frames into a normal CursorFollow output window.
  • Verify the output window appears in Teams, Zoom, Slack, Google Meet/Chrome, Edge, and OBS window-sharing pickers.
  • Confirm a real webcam can remain selected while sharing the CursorFollow output window.
  • Document chosen rendering path, output-window behavior, installer implications, and unsupported clients.

Phase 1: Project Skeleton and Tray UI

  • Create CursorFollowWin solution structure, build scripts, and baseline app.
  • Implement system tray icon, compact panel, settings dialog, persisted settings, and app startup registration.
  • Match macOS visual hierarchy and naming while using Windows 11 placement and interaction rules.

Phase 2: Window Tracking and Capture

  • Enumerate visible capturable windows with app identity and geometry.
  • Implement manual selection, filter modes, refresh, foreground-window auto-follow, cursor-under-window follow if viable, and debounce.
  • Capture selected window with Windows Graphics Capture and render the output preview.

Phase 3: Live Output Pipeline

  • Bridge captured frames into the output-window rendering path.
  • Handle resize, aspect ratio, idle state, missing window, protected content, hide/show, and pin-on-top behavior.
  • Measure latency, CPU, GPU, dropped frames, and memory behavior.

Phase 4: Packaging and Hardening

  • Create installer, upgrade path, uninstall cleanup, code signing plan, and developer verification scripts.
  • Add reset/troubleshooting docs for capture permission, output-window sharing, hotkey conflicts, and protected/elevated windows.
  • Run 30-minute stability tests and meeting-app window-sharing compatibility matrix.

Risks and Open Questions

Risk Impact Mitigation
Meeting apps differ in how they enumerate, crop, and retain shared windows. The output window may appear inconsistently, lose sharing on hide/minimize, or scale poorly. Run Phase 0 first and maintain a window-sharing compatibility matrix before committing to full architecture.
Some windows cannot be captured because of DRM, elevation boundaries, protected content, or OS restrictions. User may see black output or missing windows. Detect and explain protected/unavailable targets; keep the output window stable with fallback output.
GPU texture sharing into the output renderer may be complex. CPU copy path could raise latency or CPU usage. Prototype both minimal GPU and CPU paths; choose the simplest path that meets performance targets.
Windows startup and installer behavior may need signing or careful per-user setup. Developer setup and user install flow could be brittle. Document privilege requirements early and keep install/uninstall/reset commands repeatable. Avoid camera registration in the first Windows path.
Visual parity may conflict with native Windows expectations. App may feel either non-native or unlike CursorFollowMac. Prioritize product hierarchy and control names from macOS, but use Windows placement, focus, notification, and accessibility behavior.

Verification Checklist

Developer Verification

  • Build CursorFollowWin from a clean checkout on Windows 11.
  • Install the app and confirm the tray icon appears after launch.
  • Confirm the CursorFollow output window appears in supported meeting-app window-sharing pickers.
  • Confirm a real webcam can remain selected while the CursorFollow output window is shared.
  • Capture a selected window and verify the same content appears in the output window and meeting-app share preview.
  • Switch active windows with auto-follow enabled and confirm the output follows within the interruption target.
  • Stop capture and confirm the output window shows a graceful idle state.

Acceptance Criteria

  • Feature parity is documented and implemented for the primary macOS workflows.
  • Tray panel and settings dialog look recognizably like CursorFollow while feeling appropriate on Windows 11.
  • Meeting apps can share the CursorFollow output window and display live window content while the user's real webcam remains active.
  • Missing permissions, unsupported windows, and target disappearance degrade gracefully.
  • Build, install, verify, reset, and uninstall steps are documented and repeatable.
  • Thirty-minute capture stability test passes without crash, major leak, or sustained performance spike.
