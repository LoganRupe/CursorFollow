Shared Window V1 Requirements

Define CursorFollow as a macOS utility that tracks a target window and renders it into a normal, shareable output window.

Branch: feature/shared-window-output
Status: Planned
Primary change: remove the virtual-camera requirement from the initial product path.

Objective

CursorFollow should let a user share a single stable window in their conferencing app while CursorFollow automatically updates that window with the currently selected target window content.

The user experience should feel like: start CursorFollow, choose an output window in the conferencing app's screen-share picker, and let CursorFollow keep that output pointed at the right source.

Why This Direction

Previous camera path Shared-window path
Requires CoreMediaIO extension discovery, signing, app groups, and host-to-extension IPC. Uses a normal app window and ScreenCaptureKit capture already owned by the host app.
Appears as a camera tile, which can conflict with user expectations and camera-client quirks. Appears as a screen share, matching the actual interaction: sharing app/window content.
Higher setup burden and more OS-specific failure modes. Lower distribution complexity and easier local debugging.

Functional Requirements

  1. CursorFollow creates a visible macOS window named CursorFollow Output or equivalent.
  2. The output window renders the selected target window's live content with low latency.
  3. The output window is selectable in common conferencing screen-share pickers as a normal window.
  4. The app can track either the frontmost eligible window or a manually selected target window.
  5. The app excludes its own output and control windows from target selection to prevent recursive capture.
  6. When the target window changes, disappears, minimizes, or moves to another Space, the output window remains stable and shows an understandable fallback state.
  7. The user can pause/resume output without closing the share window.
  8. The user can choose a basic fitting mode: fit, fill, or actual size.
  9. The app surfaces missing Screen Recording permission states in the host UI.
  10. The app preserves the output window identity across target switches so conferencing apps do not need the user to reselect a share source.

Non-Functional Requirements

Area Requirement
Latency Target <50 ms median from capture callback to visible output update.
Stability No crash, runaway memory growth, or sustained CPU spike during a 30-minute continuous share session.
Target switching Visible output recovers within 300 ms after a valid target switch.
Window identity The output window should not be destroyed and recreated during normal target changes.
Distribution No camera extension, PlugInKit registration, or CoreMediaIO entitlement path is required for V1.

Scope

In Scope

  • Output-window rendering for captured frames.
  • Target-window selection and auto-follow behavior.
  • Basic output controls: pause/resume, fit mode, window size presets.
  • Permission state detection and user-facing status.
  • Validation in at least two conferencing apps or browser-based meeting tools.

Out of Scope

  • Appearing as a camera source.
  • CoreMediaIO extension setup, PlugInKit discovery, or camera-client compatibility.
  • Remote control of conferencing app share pickers.
  • Audio capture or virtual microphone support.
  • Advanced compositing, overlays, transitions, or presenter layouts.

Permissions

  • Screen Recording: required to capture other windows.
  • Accessibility: out of scope unless a future implementation adds AX APIs.
  • Camera: not required for Shared Window V1.

Key Edge Cases

  • Recursive capture if CursorFollow targets its own output window.
  • Target window becomes minimized, hidden, closed, or moved to a different Space.
  • Full-screen apps with Space boundaries and capture availability differences.
  • Conferencing apps that hide or deprioritize small, occluded, minimized, or transparent windows in share pickers.
  • Retina scaling and aspect-ratio mismatch between target and output window.

Acceptance Criteria

  1. Launch CursorFollow and show a persistent output window.
  2. Select or auto-follow a target window and see its live content in the output window.
  3. Share the output window in at least one browser meeting tool and one native conferencing app.
  4. Switch target windows without the conferencing app losing the shared source.
  5. Close or minimize the target window and see a stable fallback state rather than a crash or frozen misleading frame.
  6. Verify CursorFollow does not select its own output window as a target.
Product note: this approach creates a shareable window, not a camera source. The user still chooses that window from the conferencing app's screen-share UI.
