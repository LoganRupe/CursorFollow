Shared Window V1 Plan

A phased implementation path for replacing virtual camera output with a persistent macOS output window.

Branch: feature/shared-window-output
Implementation principle: keep capture and tracking in the host app; render to one stable output window that meeting apps can share.

Target Architecture

CursorFollowMac.app
├── AppCoordinator
│   ├── WindowTracker
│   ├── CaptureEngine
│   └── OutputWindowController
│       └── CursorFollow Output window
│           └── OutputFrameView / Metal-backed renderer
└── User shares CursorFollow Output from conferencing app

The camera extension, CoreMediaIO provider, and host-to-extension frame transport are not part of V1. The output surface is a standard app window owned by CursorFollow.

Implementation Phases

Phase 0: Product Pivot and Project Cleanup

Goal: make the shared-window path explicit in docs and code before adding more product surface area.

  1. Keep Docs/CameraExtensionV2/ as historical reference.
  2. Add Shared Window V1 docs and make them the active plan in docs navigation.
  3. Document the branch and decision record for the pivot.
  4. Identify reusable host-app pieces and remove launch-time dependencies on the camera-extension path.
  5. Record a file-level checklist for the first implementation pass.

Gate: repository docs and app startup behavior clearly identify Shared Window V1 as the current product direction.

Phase 1: Stable Output Window

Goal: create a persistent NSWindow suitable for screen-share pickers.

  1. Implement or adapt OutputWindowController to create a titled window named CursorFollow Output.
  2. Keep the output window alive across target switches and pause/resume actions.
  3. Ensure the output window is visible, non-minimized by default, and discoverable by conferencing share pickers.
  4. Add a fallback view for no target, missing permissions, paused output, and target unavailable.

Gate: the output window appears as a selectable share source in at least one conferencing app or browser share picker.

Phase 2: Frame Rendering Pipeline

Goal: render captured frames into the output window with low latency and predictable scaling.

  1. Connect CaptureEngine frame callbacks to the output renderer.
  2. Prefer a Metal-backed view or efficient Core Animation path for live frame presentation.
  3. Support fit, fill, and actual-size presentation modes.
  4. Preserve target aspect ratio and handle Retina scale correctly.
  5. Avoid frame queues that can accumulate stale frames; display the latest frame.

Gate: selected target window content appears live in the output window with acceptable visual quality.

Phase 3: Target Selection and Auto-Follow

Goal: make the output window track the intended source without selecting CursorFollow itself.

  1. Exclude CursorFollow control and output windows from target candidates.
  2. Support manual target selection from eligible windows.
  3. Support frontmost-window auto-follow with debounce to avoid rapid switching.
  4. Handle disappearing or minimized windows by keeping the output window stable and showing a clear state.
  5. Keep target-switch recovery under the 300 ms goal where ScreenCaptureKit allows.

Gate: target switching works repeatedly without recursion, crashes, or share-source loss.

Phase 4: Controls, Status, and Validation

Goal: make the app usable during real calls.

  1. Add menu bar controls for output window show/hide, pause/resume, fit mode, and target mode.
  2. Show permission status and a direct path to System Settings when capture permissions are missing.
  3. Validate behavior in Zoom, Google Meet, Slack Huddles, or Teams as available.
  4. Run a 30-minute continuous share test and record CPU, memory, and visual stability notes.
  5. Update README and docs with the shared-window workflow.

Gate: CursorFollow can be used in a real meeting by sharing the persistent output window.

Phase 0 Inspection Notes

The current host app already contains several pieces needed for Shared Window V1. WindowTracker enumerates ScreenCaptureKit windows, filters system and CursorFollow-owned windows, supports manual selection, and auto-follows frontmost-window changes with debounce. CaptureEngine already captures a selected SCWindow at bounded dimensions with quality presets and low queue depth. OutputWindowController already creates a persistent titled NSWindow named CursorFollow Output and renders an IOSurface through a Core Animation layer. ContentView already exposes show/hide, start/stop, filtering, settings, and hotkey-related controls.

The remaining Phase 0 cleanup is mostly product alignment: the app still imports and activates the camera system extension on launch, the capture path is named and documented as extension frame transport, host entitlements still include system-extension install and app-group concerns, and the output window lacks explicit fallback states and fit-mode controls required by the V1 requirements.

Rendering Options

Option Pros Cons Recommendation
Metal-backed view Best long-term path for low-latency frame presentation. More setup and texture conversion work. Preferred if existing frame format is easy to bridge.
Core Animation layer Simple integration with AppKit/SwiftUI window content. May require careful testing for latency and color correctness. Good first implementation if it keeps the code small.
SwiftUI Image updates Fast to prototype. Likely less efficient for continuous video frames. Use only for fallback/prototype, not final V1.

Validation Checklist

  • Output window appears in macOS window list and conferencing share pickers.
  • Output window remains the same share source after target switch.
  • CursorFollow never captures its own output window.
  • Missing Screen Recording permission shows fallback state.
  • Full-screen and Space-boundary behavior is documented.
  • 30-minute session shows no major memory growth or frame stall.
Risk to test early: some conferencing apps may hide windows that are fully occluded, minimized, or on another Space. Keep the output window visible and test the share picker before investing in polish.
